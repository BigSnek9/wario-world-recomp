## A001 - Early MMIO/register divergence in SDK initialization (verifier issue resolved)

Run: `python scripts/smoke_boot.py --seconds 8 --lockstep`.
Diagnostic run directory: private/runs/20261024T230839922540Z (UTC name).
Main module: MSVC portable C, generated by the runtime's bundled DolRecomp.
Verifier enabled with dispatch limit 10000, normal deduplication and max 10 reports.

First reported entry 0x801A00B8, native endpoint 0x801A0430.
Reported differences: r0/r3/r4/r5/r6/r7, LR, CR and MMIO journal count.
Native MMIO addresses use 0xCC00... aliases while the shadow report includes
0x0C003004. The register values and full journal text are in the private log.

Resolution: the native block inlines iterations of the interrupt-mask loop,
returning at 0x801A0430. The backward branch at 0x801A0434 targets 0x801A0428;
the old detector recognized only a target equal to the end PC and stopped the
shadow at the first visit to 0x801A0430. MMIO aliases were already normalized in
the journal comparison and were not the cause. Correcting the local-loop-interior
boundary detection removes this report without changing guest code or filtering.

## A002 - Thread initialization loop divergence (verifier issue resolved)

Same run; entry 0x801A3004, endpoint 0x801A3020. r3/r29/r30 and CR differ.
The native block inlines queue initialization iterations and returns at
0x801A3020; the branch at 0x801A302C targets 0x801A3018. The old shadow stopped

synthetic branch/continuation cases pass against the actual production detector,

## Evidence limits

### Existing fallback counter omits JIT execution (A006)

StaticRecompCore_Run.cpp counts forced/interpreter steps but does not count
m_fallback_jit->Run(). Earlier fallback=0 reports therefore cannot establish zero
JIT use. A paused snapshot from run 20261025T103819667331Z contains linked
WWUSTT module ID 8 at header 0x804AF580; executable section 3 is 0x804AF678,
size 39244. The main-only DLL cannot execute that section natively. Added a
separate JIT-entry counter/histogram; it counts transfers, not instructions.

### REL mapping and verification gaps (A007)

The observed linked header +0x10 holds an absolute section-table pointer.
RefreshRelSections instead requires the original file offset at +0x10, so linked
headers fail its match. Cached sections also require unload/reload validation.
Metadata covers code sections only: audit data/BSS relocations and LR/CTR values.
VerifyChunk learns a first runtime hash when the expected hash is zero; this is
not independent validation of relocated code. Do not use zero-hash metadata as
a shortcut to claim complete static coverage.

Data-section update, 2026-10-25: audit_loaded_rel.py now also compares every
initialized (non-BSS) data section of a linked module against the independent
relocation model, classifying byte differences by whether the containing word is
a relocation write site. For the observed linked WWUSTT snapshot, all 145 data
relocation sites (sections 4, 5 and 7) still hold the modeled link values, and
the single non-site difference is the vtable boundary marker word at section 7
offset 0 changing 0xFFFFFFFE to 0xFFFFFFFF (guest mutation of mutable data).
Remaining gap: this covers the one module observed linked in that snapshot at
one point in time; unload/reload and the other modules need the same check.

The initial lockstep run made 228 checks and reported 2 differences. After the
detector correction, run private/runs/20261024T231317787136Z makes 228 checks,
reports 0 differences, skips 16 fallback cases and 1 zero case, and has zero
step-cap hits/undercharge reports.
Those counts describe this short diagnostic only; they are not game coverage.
Null graphics and muted audio establish no pixel/audio accuracy. Reported frame
and present counts are runtime counters whose cadence still requires validation.

## A009 - Memory card writes fail; menu path to gameplay blocked

Automated probes reach the file-select hall but data creation always fails, so
gameplay (and with it runtime execution of REL modules 1-7) cannot be reached
through the menus yet.

Observed flow (private runs 20261025T125052430561Z through 20261025T134738164027Z,
clean full-port DLL, fresh user folder each run, input via pad_frames automation):
- title -> Start -> file-select hall renders correctly;
- banner "There are no data files for this game on the Memory Card in Slot A.";
- A opens "Create a file ... ?" (Yes default); Yes runs the creation animation,
  fails, and returns to the banner;
- after idle the hall shows "The game cannot be saved. Continue anyway?";
  the file screen times out to the title screen if left unanswered;
- the menu state cycles autonomously roughly every 30 seconds.

Configurations tested: default GCI folder card (user/GC/USA/Card A, empty, no
.gci ever written) and raw card (user/Config/Dolphin.ini [Core] SlotA=1; a
16 MiB MemoryCardA.USA.raw appears only at shutdown, never during play). Both
fail identically, so the failure is not folder-versus-raw specific. No memcard
error is logged. In reference Dolphin, first-boot creation on an empty card is
expected to succeed; an installed standalone Dolphin 2606a was subsequently located. An isolated
comparison is now in progress; earlier assertions of expected behavior were
not measured evidence.

Suspect: runtime memory-card/EXI emulation defect, not the static recomp CPU.
Decisive comparison, run 20261025T135447110723Z: the identical probe under
--reference (same runtime, original-code JIT CPU) fails the same way with the
same menu cycle, so the divergence exists with the runtime's own interpreter
too. Next step is EXI-level tracing of the format/write transaction in the
runtime (compare against Dolphin's EXI_DeviceMemoryCard behavior), not CPU
verification. The newly added [wario-exi] device-enum log (RecompCore.patch)
confirms which device is configured. Do not work around this by patching the
game or fabricating save files. smoke_boot.py --memcard raw and
scripts/classify_captures.py (pixel-nearest state classification of captures)
were added for this investigation.

EXI protocol trace, 2026-10-25 (runs 20261025T135849225189Z through
20261025T140624367224Z, instrumented [wario-mc] fprintf in
EXI_DeviceMemoryCard.cpp, captured in RecompCore.patch):
- mount sequence per attempt: 00 NintendoID, 89 ReadID, 83 ReadStatus,
  81 ClearStatus, then ReadArray + EXI DMA sector reads;
- the game DMA-reads the full system area 0x0000-0x9FFF in 512-byte sectors,
  four passes, 320 reads per 90 s session;
- returned content is a CORRECTLY formatted empty card: valid header checksum
  (38c0f979) at 0x0000, directory blocks (0x2000/0x4000) with the expected
  all-FF free entries, BAT blocks (0x6000/0x8000) with checksum 07ff/e803 and
  zeroed map. The card ID response carries size_mbits (0x80 for 128 Mbit),
  matching upstream Dolphin behavior;
- across the whole session, including three "Create a file? Yes" attempts,
  there are ZERO SectorErase/PageProgram/ChipErase commands: the game's SDK
  declines to write on a card whose readable content is valid.
Interpretation: EXI transport, DMA and card formatting all look correct; the
failure is in whatever the game's SDK checks after/around reading - candidates:
EXI command-completion interrupt latency (CmdDoneLater 5000 cycles vs SDK
timeouts), the 2-byte ReadID/NintendoID values, or a subtle field in the
formatted header (flash ID, encoding, size fields). Next session: log the full
tail bytes of each directory/BAT DMA read to verify the checksums the game
sees, and instrument CmdDone/TransferComplete interrupt latency. Do not work
around this by patching the game or fabricating save files.
smoke_boot.py --memcard raw and scripts/classify_captures.py (pixel-nearest
state classification of captures) were added for this investigation.
Comparison note: the traced TransferByte/DMARead/DMAWrite logic in this fork
matches upstream Dolphin master line-for-line in the relevant paths, so the
defect is expected in the fork's EXI interrupt/timing integration (EXI_Channel,
EXI.cpp UpdateInterrupts, CoreTiming pacing under the recomp runtime) or in a
game-SDK timing assumption, not in the card command state machine.

## A010 - Verifier restores stale MSR translation mode (fixed in C overlay)

## A011 - Windows headless graphical startup requires a hidden HWND

The old HeadlessPlatform gave OpenGL no Windows rendering surface, causing
startup to stall before CPU frames. Headless graphical rendering now uses a
Win32 surface that is never shown or activated; Null retains HeadlessPlatform.
Headless alerts go to stderr and panic exits rather than opening a dialog;
No Audio Output remains selected. This is a host test-harness repair, not a
change to guest timing or framebuffer data. Run 20261026T104538740504Z:
120 seconds, 6043 checks/zero reports/JIT entries, 59.94 FPS/VPS. The visible
window inventory was empty during rendering. Project rule: silent hidden tests.

## A012 - Differential coverage must follow code-mapping lifetime (fixed)

PC-only deduplication could skip newly loaded code at reused REL addresses.
The verifier now records generation per PC, captures generation at Prepare,
and rechecks after mapping changes or ClearCache/state restoration. Compiled
production predicates have nine regression cases (1 fails before, 0 after).
The Greenhorn transition passes 12785 checks / zero reports under this repair.
Previously reported checks are limited historical coverage, not invalidated CPU
comparisons; code/context coverage was weaker than the PC count suggested.

## A013 - Snapshot REL audits must exclude stale unlinked headers (fixed)

The inspector's raw header scan was candidate discovery only; the auditor had
selected all absolute headers, including potential stale allocations. Audits now
validate the live OSLink head/tail/backlinks and require candidates to belong to
that queue. Empty queues report zero active modules/REL bytes. Greenhorn uses
main code, with no linked REL in the snapshot; all main text bytes match original.

## A014 - Probe frame origin after state load (harness limitation)

The renderer frame counter is restored from state. The first new resume probe
could queue steps against stale pre-load status. The harness now waits for a
processed load command plus settled post-load status before setting its relative
origin. This is adequate for behavioral navigation but is not input-poll-exact
replay. Resume tests use copied genuine private user data; no save fabrication.
