# Open accuracy and coverage issues

No bit-accuracy claim is made. Reproduce these before choosing fixes; do not
silence the validator or force fallback to make the reports disappear.

## A001 - Early MMIO/register divergence in SDK initialization (verifier issue resolved)

Run: `python scripts/smoke_boot.py --seconds 8 --lockstep`.
Diagnostic run directory: private/runs/20261024T230839922540Z (UTC name).
Main module: MSVC portable C, generated by the runtime's bundled DolRecomp.
Verifier enabled with dispatch limit 10000, normal deduplication and max 10 reports.

First reported entry 0x801A00B8, native endpoint 0x801A0430.
Reported differences: r0/r3/r4/r5/r6/r7, LR, CR and MMIO journal count.
Native MMIO addresses use 0xCC00... aliases while the shadow report includes
0x0C003004. The register values and full journal text are in the private log.

Resolution: the native block inlines iterations of the interrupt-mask loop,
returning at 0x801A0430. The backward branch at 0x801A0434 targets 0x801A0428;
the old detector recognized only a target equal to the end PC and stopped the
shadow at the first visit to 0x801A0430. MMIO aliases were already normalized in
the journal comparison and were not the cause. Correcting the local-loop-interior
boundary detection removes this report without changing guest code or filtering.

## A002 - Thread initialization loop divergence (verifier issue resolved)

Same run; entry 0x801A3004, endpoint 0x801A3020. r3/r29/r30 and CR differ.
The native block inlines queue initialization iterations and returns at
0x801A3020; the branch at 0x801A302C targets 0x801A3018. The old shadow stopped
at the continuation after the first call, while the native block had completed
more iterations. The same detector correction removes this report. Eight
synthetic branch/continuation cases pass against the actual production detector,
including negative cases for backward calls and unrelated later loops.
No guest patch, validator whitelist, mismatch filter or fallback override used.

## A003 - Hidden instruction-level interpreter dependency

The initial 20-second Null-renderer boot reports native=63189880 and fallback=0,
but hook_fb=1033441. The latter counter is incremented in HookInstructionFallback
and executes an interpreter helper for unmodeled hardware/system instructions.
Thus fallback=0 alone is insufficient evidence of static-only execution.
That run reports smc_failed=0 with 68 chunk verifications; unvisited code remains
unverified. Hook fallback was not classified at that checkpoint.

Update 2026-10-25: run 20261025T103819667331Z identifies 14 sites: HID0
read/write (four sites), L2CR read/write (two), decrementer write (one), WPAR
write (one), dcbf (two), dcbst (two), dcbi and icbi (one each). All traced words
match the paused MEM1 snapshot. These are observed boot/menu sites only.
The six cache sites use an existing direct fast path when data-cache emulation
is disabled; system-register operations can enter the interpreter. The helper
counter aggregates both paths. Preserve hardware side effects and cycle costs.

## A004 - Missing compiled REL integration

All eight original RELs translate as local C artifacts with zero unknown-opcode
reports after the empty-section fix. The current loaded DLL includes main DOL
only. It is not full Wario World static recompilation.

Runtime source has section-mapping metadata and searches for active REL headers;
the port builder/module-template does not automatically bundle these eight RELs.
In particular, audit relocated immediates, branch targets/LR values, memory
references, section-table mutation by OSLink, unload/reload, code hashes and
mapping invalidation before using synthesized link bases.

## Evidence limits

### Existing fallback counter omits JIT execution (A006)

StaticRecompCore_Run.cpp counts forced/interpreter steps but does not count
m_fallback_jit->Run(). Earlier fallback=0 reports therefore cannot establish zero
JIT use. A paused snapshot from run 20261025T103819667331Z contains linked
WWUSTT module ID 8 at header 0x804AF580; executable section 3 is 0x804AF678,
size 39244. The main-only DLL cannot execute that section natively. Added a
separate JIT-entry counter/histogram; it counts transfers, not instructions.

### REL mapping and verification gaps (A007)

The observed linked header +0x10 holds an absolute section-table pointer.
RefreshRelSections instead requires the original file offset at +0x10, so linked
headers fail its match. Cached sections also require unload/reload validation.
Metadata covers code sections only: audit data/BSS relocations and LR/CTR values.
VerifyChunk learns a first runtime hash when the expected hash is zero; this is
not independent validation of relocated code. Do not use zero-hash metadata as
a shortcut to claim complete static coverage.

Data-section update, 2026-10-25: audit_loaded_rel.py now also compares every
initialized (non-BSS) data section of a linked module against the independent
relocation model, classifying byte differences by whether the containing word is
a relocation write site. For the observed linked WWUSTT snapshot, all 145 data
relocation sites (sections 4, 5 and 7) still hold the modeled link values, and
the single non-site difference is the vtable boundary marker word at section 7
offset 0 changing 0xFFFFFFFE to 0xFFFFFFFF (guest mutation of mutable data).
Remaining gap: this covers the one module observed linked in that snapshot at
one point in time; unload/reload and the other modules need the same check.

The initial lockstep run made 228 checks and reported 2 differences. After the
detector correction, run private/runs/20261024T231317787136Z makes 228 checks,
reports 0 differences, skips 16 fallback cases and 1 zero case, and has zero
step-cap hits/undercharge reports.
Those counts describe this short diagnostic only; they are not game coverage.
Null graphics and muted audio establish no pixel/audio accuracy. Reported frame
and present counts are runtime counters whose cadence still requires validation.

## A005 - Renderer startup and shutdown coverage

Headless Vulkan run private/runs/20261024T230936588055Z produced zero frames and
required termination of the diagnostic child process; cause remains unverified.
OpenGL windowed rendering works. The first windowed run's shutdown stalled due

## A008 - Generated-code FMA status mismatch (fixed for current GXRuntime)

Exact-instruction-count run 20261025T105300424742Z: 5403 checks, 29 reports,
24 helper skips, 36 zero skips. Printed differences are FPSCR FI (bit 17).
Generated C calls ppc_fma, which discarded pre-rounding information needed by
fmadds and did not apply NI single rounding like the opcode helper.
verify_fma.py compares both production helpers across eight operation modes,
four initial FI/FR patterns, two NI modes and eight operand sets. Before repair:
59/512 discrepancies; afterward 0/512. Repair reuses the runtime's existing
NI arithmetic and rounding helpers, preserves invalid-operation gating, and
updates FI/FR for fmadds consistently with the opcode path.

Repeat 20261025T105720807268Z: exact_instruction_count=1, 5401 distinct-PC
checks, 0 reports, 24 helper skips, 35 zero skips, 0 cap hits, 0 filters,
0 undercharges. Clean exit, 70 verified chunks, no failed SMC chunks.
JIT still entered 852734 times at 438 entry PCs: this is partial CPU validation.
No game-derived code or original input was patched to hide a difference.

The standalone DolRecomp CPU library differs from GXRuntime; its own tests are
not an independent oracle for these status flags. The runtime repair applies
to the actual GXRuntime used by native DLLs. Keep separate tool/runtime evidence.
